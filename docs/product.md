# 产品愿景

> 本文件是 Chalkline 的长期产品上下文，每次 Agent 交互都会注入。只写稳定的内容；版本计划与具体需求属于迭代与任务，不进这里。

## 定位

面向 5–50 人研发团队的 SDD 协作平台：把产品、模块、迭代、任务组织进可定制的工作流，用服务端门禁保证规格先行、评审留痕，让团队成员的编码 Agent 通过 MCP 接入同一份事实，而不是各自在聊天框里推动 AI。

一句话：**给 AI 开发装上流程和门禁，让人只负责裁决。**

## 目标用户

| 角色 | 痛点 | 在 Chalkline 里做什么 |
| --- | --- | --- |
| 产品经理 | 需求散在文档与聊天里，不知道实现到哪一步 | 定义产品与模块、创建迭代、拆解任务、确认需求门禁 |
| 评审人 / 技术负责人 | 评审靠口头，事后无法追溯 | 在门禁处确认或驳回，查看材料 |
| 开发者 | 每次都要手动喂上下文推动 AI | 让 Agent 调 `get_next_action` 自己拿到下一步 |
| 测试工程师 | 测试设计与执行无痕迹，报告散落 | 走测试任务流程，用例、执行记录、报告挂在门禁上 |
| 团队负责人 | 看不到整体进展 | 控制台看迭代燃尽、门禁积压、成员负载 |

## 核心能力

1. **全生命周期覆盖**：每个迭代就是一条完整生命周期——从竞品调研、关键技术调研、产品规划，到研发、测试设计、测试执行、测试报告，直到迭代与任务总结，全部纳入流程与门禁。
2. **组织模型**：产品 → 多个迭代（并行或串行）→ 多级任务，模块多级且任务可跨模块，任务指派唯一负责人，编号多级且不可变。
3. **可定制工作流**：迭代与任务两层各自选模板，节点、连线、门禁均以 YAML 定义。内置模板只是默认配置，可编辑、复制、另建。
4. **服务端门禁**：门禁通过需指定角色确认 + 指定材料上传，缺一不可，状态机拒绝越级。
5. **读开放、写收敛**：全员可读所有产品、迭代与任务；写权限按角色与负责人判定，门禁审批只认持有对应角色的人，越权在服务端拒绝。
6. **并行推进**：工作流是 DAG，调研与规划、研发与测试设计可以同时进行，汇合点按「全部完成」才放行。
7. **Agent 原生接入**：MCP over HTTP，多用户并发，一个实例，无需桥接与手工同步。
8. **控制台**：以进度为中心——产品阶段、迭代看板、任务树、审批队列。
9. **全程留痕**：每次状态流转、审批、材料上传都记录操作者、时间与理由。
10. **集成而非内置**：代码、文档、进度、通知继续用团队已有的工具（Git/SVN、Outline、Redmine、邮件），平台只存引用与事件，不复制内容。

## 设计原则

- **门禁强制力优先于自动化程度**：宁可少自动化，也不能让流程可以被绕过。
- **服务端裁决，客户端建议**：Agent 可以提议、起草、执行，但不能自行判定通过。
- **流程是数据，不是代码**：工作流以配置表达，新增流程不改引擎代码。
- **人的位置在裁决点**：人不参与搬运信息，只在门禁处做判断。
- **只为流程负责**：成果物、代码、文档、通知都由外部工具承担，平台只保存引用与事件。
- **默认收敛**：接口返回结构固定、状态有限、错误可读；不做开放式 DSL 与插件系统。

## 非目标

- 不做 Agent 编排与模型调用（那是编码 Agent 的事，Chalkline 只给流程与数据）。
- 不做通用项目管理（甘特、财务、工时核算、OKR）。
- 不做代码托管、CI 执行、文档知识库、通知门户（只存引用与事件）。
- 不做多租户 SaaS（单部署服务一个团队，多实例靠部署隔离）。

## 成功标准

- 一个迭代从立项到收尾全程在平台留痕，任务状态无需口头同步即可获知。
- Agent 在无人干预下能连续推进多个步骤，仅在门禁处停下等人。
- 规格与实现的偏差在评审门禁处被发现，而不是在交付后。
